# План: поддерживаемая ОС для relay и точки проверки

Статус: **план, не выполнялось**. Запуск только по отдельному решению владельца.

## Зачем

Relay — единственный путь бота к MAX API и единственная точка проверки доступности нод.
Его ОС снята с поддержки: исправления безопасности не приходят. Простой relay означает,
что бот молчит, а отметки доступности через три часа исчезают; сами VPN-подключения не страдают.

## Что усложняет обновление на месте

На том же хосте работают посторонние для проекта сервисы: веб-сервер, приложения с фоновой
очередью, PostgreSQL и Redis. Обновление major-версии ОС для них означает:

- новую major-версию PostgreSQL — нужен отдельный перенос кластера, старый не обновляется сам;
- новую версию системного Python — виртуальные окружения приложений придётся пересобирать;
- замену конфигурации веб-сервера и сторонних репозиториев пакетов.

Откатить обновление ОС на месте нельзя, только восстановлением снимка диска.

## Вариант A (рекомендуется): вынести роль на отдельный маленький хост

1. Новый минимальный сервер внутри той же сети с ограничениями, на поддерживаемой ОС.
   Лучше у **другого провайдера**: это заодно даёт вторую точку проверки доступности.
2. Установить relay по `infra/max-relay/` с новым ключом; добавить ключ на jump-узел рядом со старым.
3. Проверить из контейнера бота `GET /me` и подписки через новый relay, не выключая старый.
   Одновременно держать сокет может только один relay: переключение — остановить старый, запустить новый.
4. Установить точку проверки по `infra/rf-probe/README.md`, добавить её в `RF_PROBE_VANTAGES`.
5. Наблюдать сутки, затем отключить юнит на старом хосте и удалить там ключи и цели проверки.

Откат на любом шаге: запустить прежний юнит. Посторонние сервисы старого хоста не затрагиваются.

## Вариант B: обновление на месте

Только вместе с владельцем остальных сервисов и в согласованное окно.

1. Снимок диска у провайдера и проверка, что из него можно восстановиться.
2. Дампы всех баз, копии конфигураций, список установленных пакетов и включённых юнитов.
3. Обновить текущий выпуск до последних пакетов, перезагрузить, убедиться, что всё поднялось.
4. Сменить источники пакетов на следующий выпуск (сторонние репозитории — тоже), выполнить
   минимальное, затем полное обновление; на вопросы о конфигурационных файлах оставлять свои.
5. Перенести кластер PostgreSQL на новую major-версию, пересобрать окружения приложений.
6. Перезагрузить. Проверить: relay active и бот получает 200 от MAX; прогон проверки доступности
   без остатков; каждый посторонний сервис — по списку его владельца.
7. Пропускать выпуски нельзя: при отставании на два выпуска шаги 3–6 повторяются дважды.

Ожидаемый простой: десятки минут для relay, дольше для баз. Откат — только снимок диска.

## До решения

- Автоматические обновления безопасности текущего выпуска оставить включёнными.
- На хосте ничего, кроме relay и проверки, от имени проекта не размещать.
