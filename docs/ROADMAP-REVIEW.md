# Разбор найденного roadmap 2026-11-11

Изучен полный локальный документ «Pachca VPN Bot — бизнес-план и роадмэп», версия 1.0.
Его статус: **черновик, к реализации не утверждён**. Приватный оригинал остаётся вне публичного Git:
он содержит корпоративную топологию, названия пространств и организационные детали.

## Что на самом деле предлагалось

Отдельный корпоративный бот: сотрудник запрашивает VPN, уполномоченный подтверждает,
бот выдаёт конфиг, затем поддерживает lifecycle и увольнение. Оплат нет.
Транспорт-кандидат — Pachca SSE + история событий, fallback webhook с подписью.
Один bot token на пространство, раздельный scope/данные; MAX не заменяется.

В исходном плане этапы: решения/доступы → каркас → заявки/approval → выдача/замена →
offboarding → optional аудит/продление → deployment → ограниченный пилот → масштабирование.
Старые оценки трудозатрат не переносим как обещание: API/зависимости нужно проверить заново.

## Что переиспользовать

| Идея | Применимость |
|---|---|
| Panel adapter и awg/awg3 | да, с pinned contract tests |
| ownership, quota, durable operations, replacements | сохранить инварианты; не копировать все MAX-поля механически |
| request/approval state machine | отдельный corporate workflow, не обязательный шаг платной выдачи MAX |
| offboarding/полный отзыв | ценно; success доказывается состоянием нод, не blocked flag |
| повторная проверка approver/identity | обязательна для любого нового транспорта |
| SSE/history dedup и renew URL | новая транспортная логика; ещё не реализована |
| автоматическое удаление сообщения с конфигом | отдельно проверить права/реальный API и UX; не обещать до live test |
| нагрузочные цифры и capacity | гипотеза, не измеренная гарантия |

## Обязательные решения до corporate-кода

1. Интернет-egress или внутренний доступ; отдельные ноды/панель и границы ответственности.
2. Кто подтверждает: выделенная admin/approver группа либо надёжно определённый руководитель.
3. Hosting и transport; отдельные credentials и запрет смешивать personal/corporate DB.
4. Quota/TTL/продление, пространства, аудит/retention и действия при offboarding.
5. Фактические возможности текущего Pachca API: signature, сроки trigger/form,
   event history, uploads, deletion, rate limits — перепроверить по официальной документации.

Предпочтение исходного draft: независимый сервис на основе проверенных идей, а не преждевременная
общая библиотека с связанными релизами. Сейчас этот вариант не превращён в утверждённую архитектуру.

## Вывод для текущей модернизации

Сначала Git/build/restore/observability и защита существующего личного MAX-сервиса.
Затем выбирать продуктовые изменения. Не вырезать billing ради переноса corporate-идей и
не подключать ещё один канал к единственной SQLite параллельным writer без redesign.
