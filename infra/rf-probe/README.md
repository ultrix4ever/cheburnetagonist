# Проверка доступности VPN из сети с ограничениями

Отвечает на вопрос «может ли клиент внутри России реально пользоваться каждой нодой».
Проверка состояния нод панелью этого не показывает: нода может работать и быть недоступной для клиентов.

## Как устроено

```
operator host (systemd timer, collect.py)
   │ ssh                                   │ ssh
   ▼                                       ▼
vantage host внутри сети с ограничениями    manager
probe.py: настоящий VPN-клиент             docker exec … python -m vpnmax.cli reachability
   │ UDP                                   │
   ▼                                       ▼
VPN-ноды                                   реестр бота → владелец и пользователи в MAX
```

- **`probe.py`** работает на vantage host. Для каждой ноды поднимает клиент AmneziaWG во временном
  network namespace и проверяет по порядку: рукопожатие → ICMP через туннель → HTTPS через туннель.
  В namespace живёт только интерфейс туннеля, поэтому маршруты самого хоста не меняются.
  Результат — JSON в stdout и в `/var/lib/rf-probe/latest.json`.
- **`collect.py`** работает на operator host, который видит обе стороны по SSH. Vantage host и manager
  могут не видеть друг друга. Через скрипт не проходят секреты.
- **Бот** (`apps/max-bot/vpnmax/reachability.py`) хранит состояние, пишет владельцу при изменении
  и показывает статус в списке серверов. Команда владельца: `/rf`.

Статусы результата: `ok`; `fail` со стадией `handshake`, `traffic` или `http`; `error` — сломалась сама
проверка, это не свидетельство о ноде, и бот такое не учитывает.

## Правила интерпретации

- Нода считается недоступной после **двух** неудачных прогонов подряд; один успешный сбрасывает счёт.
- Результаты старше трёх часов никому не показываются как актуальные. Если отчётов нет больше часа,
  владелец получает сообщение: молчание проверки не равно «всё работает».
- Одна точка — один провайдер в одном городе. Датацентр обычно блокируют мягче, чем мобильную
  и домашнюю связь: «подключается» не значит «работает у всех», «не подключается» — сильный сигнал.
- Поле `icmp` и статус ноды в панели помогают отличить блокировку от поломки, но не доказывают её.

## Установка vantage host

Нужны Linux с `/dev/net/tun`, `iproute2`, `ping`, `curl`, `pkill`, Python 3.9+ и root для запуска.

1. Клиентские бинарники взять **из контейнеров самих нод**, чтобы версии протокола совпадали:
   `amneziawg-go` каждой серии, `awg` и его загрузчик musl. Положить в `/opt/rf-probe/bin/`:

   | Файл | Откуда |
   |---|---|
   | `amneziawg-go-awg` | `/usr/bin/amneziawg-go` контейнера ноды серии awg |
   | `amneziawg-go-awg3` | то же для серии awg3 |
   | `awg` | `/usr/bin/awg` |
   | `ld-musl-x86_64.so.1` | `/lib/ld-musl-x86_64.so.1` (следовать symlink) |

   `amneziawg-go` статический; `awg` собран под musl и запускается через приложенный загрузчик.
   Записать SHA-256 установленных файлов в приватные заметки.
2. `probe.py` → `/opt/rf-probe/probe.py` (root, 0755).
3. Для каждой ноды выпустить в панели отдельный служебный профиль и сохранить его обычный клиентский
   конфиг в `/etc/rf-probe/targets/<id>.conf` (каталог 0700, файлы 0600, root). Первая строка файла:

   ```
   # rf-probe {"id": 1, "name": "Название для сообщений", "engine": "awg"}
   ```

   `id` должен совпадать с ID сервера в панели, `engine` — `awg` или `awg3`.
   Конфиги содержат приватные ключи: только на vantage host и в защищённой копии, никогда в Git.
4. Проверка: `sudo /opt/rf-probe/probe.py --vantage <name> --only 1`. После прогона не должно
   оставаться интерфейсов `rfp*`, namespaces и процессов клиента.

## Установка сборщика на operator host

```
install -D -m 755 collect.py /usr/local/lib/rf-probe/collect.py
install -m 644 rf-probe-collect.service rf-probe-collect.timer /etc/systemd/system/
```

Значения площадки — в drop-in `/etc/systemd/system/rf-probe-collect.service.d/site.conf`:

```
[Service]
Environment=RF_PROBE_VANTAGES=<name>=<ssh-alias>[,<name>=<ssh-alias>]
Environment=RF_PROBE_SINK_SSH=<ssh-alias manager>
```

Затем `systemctl daemon-reload && systemctl enable --now rf-probe-collect.timer`.
Несколько vantage hosts (разные провайдеры) добавляются через запятую; бот хранит их отдельно.

## Эксплуатация

- Ручной прогон: `systemctl start rf-probe-collect.service`, результат в `journalctl -u rf-probe-collect`.
- Текущее состояние: владелец отправляет боту `/rf`.
- Новая нода: служебный профиль → файл цели на vantage host. Изменений в боте не требуется.
- Смена версии VPN на нодах: обновить бинарники из контейнера ноды.
- Служебные профили видны в панели и в реестре бота как профили без владельца. Не отзывать их при уборке.
- Удаление: остановить timer, удалить `/opt/rf-probe`, `/etc/rf-probe`, `/var/lib/rf-probe`
  и отозвать служебные профили в панели.
